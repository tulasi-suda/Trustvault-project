# TrustVault Threat Model & Security Posture

This document catalogs identified security threats, technical mitigations implemented in the codebase, the automated test verifying each mitigation, and current status.

---

## 1. Verified Mitigations (Tested & Passing)

| Threat | Technical Mitigation | Automated Test Proving Mitigation | Status |
|---|---|---|---|
| **Direct modification or deletion of audit logs** | PostgreSQL `BEFORE UPDATE OR DELETE` row trigger and `BEFORE TRUNCATE` statement trigger raise exceptions. Application role lacks update/delete permissions. | `tests/schema.test.js`: *"audit_log table rejects UPDATE and DELETE via database triggers"* | **Passing** |
| **Audit log payload tampering or row deletion going undetected** | Cryptographic hash chain using SHA-256 over deterministic canonical JSON, serialized by PostgreSQL transaction-level advisory lock (`pg_advisory_xact_lock(424242)`). `verifyAuditChain()` detects any altered hash or skipped ID. | `tests/audit.test.js`: *"reports tampering when a row hash is corrupted"*, *"creates a valid genesis entry and consecutive chained entries"* | **Passing** |
| **Leaking credentials or tokens into audit logs** | `sanitizeDetails()` recursively filters forbidden keys (`password`, `confirmPassword`, `token`, `session`, `sessionId`, `content`, `file`) and sanitizes control characters. | `tests/audit.test.js`: *"never stores sensitive keys such as password or sessionId in details"*, *"sanitizes strings: strips newlines, control characters, and truncates"* | **Passing** |
| **Accidental execution of destructive test migrations on production database** | Database connection pool throws fatal exception if `NODE_ENV === 'production'` or `TEST_DATABASE_URL` does not explicitly contain `"test"`. | `tests/schema.test.js`: *"refuses to run tests if TEST_DATABASE_URL lacks 'test' or NODE_ENV is production"* | **Passing** |
| **Mass assignment privilege escalation (e.g. setting role='admin')** | Registration endpoint strictly extracts only allowed credentials and forces `role = 'user'`, `is_active = TRUE`, ignoring client-supplied roles, IDs, or flags. | `tests/auth.test.js`: *"POST /api/auth/register enforces validation, ignores role/id, returns 201, does not log in"* | **Passing** |
| **Weak passwords subject to dictionary attacks** | Server-side validation requires minimum 10 characters containing both letters and numbers; sliding-window rate limit caps registrations to 5/hr/IP. | `tests/auth.test.js`: *"POST /api/auth/register validates password complexity and password matching"*, *"POST /api/auth/register rate limits after 5 attempts per IP per hour"* | **Passing** |
| **Timing attacks to enumerate registered accounts** | Constant-time password verification using a pre-computed bcrypt dummy hash for non-existent users prior to returning generic 401. | `tests/auth.test.js`: *"POST /api/auth/login handles generic 401 for unknown user and wrong password"* | **Passing** |
| **Login credential brute-forcing** | In-memory sliding-window rate limiter tracks failed login attempts per IP. Exceeding threshold triggers generic 429 response. Successful authentication resets the failure counter. | `tests/auth.test.js`: *"POST /api/auth/login rate limiting counts ONLY failed attempts"* | **Passing** |
| **Session persistence across password change** | Changing password terminates all other active sessions for that user in PostgreSQL while preserving the current active session. | `tests/auth.test.js`: *"Profile PATCH updates fields, POST /api/profile/password deletes all OTHER sessions"* | **Passing** |
| **Document existence disclosure to ungranted users** | Single centralized authorization function (`authorize`) throws identical `NotFoundError` (404) with uniform response body for unauthorized attempts, non-existent documents, or soft-deleted files. | `tests/documents.test.js`: *"Matrix: view_metadata authorization"*, *"Matrix: download authorization and headers"* | **Passing** |
| **Administrative privilege abuse (admin reading confidential files)** | `authorize` restricts ungranted administrators strictly to `view_metadata`. Attempting file download returns 404 without reading storage contents. | `tests/documents.test.js`: *"Matrix: download authorization and headers"* | **Passing** |
| **Unauthorized document metadata modification** | Only users with `edit` grant or document ownership can update title, description, and category. All other callers receive 404. | `tests/documents.test.js`: *"Matrix: edit authorization"* | **Passing** |
| **Unauthorized document deletion or grant tampering** | Only the document owner can soft-delete or manage access grants. Editors, viewers, ungranted users, and administrators receive 404. | `tests/documents.test.js`: *"Matrix: delete authorization"*, *"Matrix: grant management is owner only"* | **Passing** |
| **Stale permission caching / race conditions** | Permissions are read directly from the database on every request without in-memory caching; grant revocation applies on the immediate next request. | `tests/documents.test.js`: *"Matrix: grant management is owner only"* | **Passing** |
| **Partial upload state when sharing with non-existent users** | Document upload, storage, recipient resolution, grant assignment, and audit entry execute in a single database transaction. Any unrecognized email fails the entire upload with 400. | `tests/documents.test.js`: *"Upload with unknown recipient email fails whole upload with 400 and creates nothing"* | **Passing** |
| **MIME type and file extension spoofing** | Server verifies both extension and file magic bytes (PDF, PNG, JPG, DOCX/XLSX ZIP headers, plain text null-byte check). | `tests/documents.test.js`: *"Upload rejects spoofed magic bytes, oversize files, and traversal filenames"* | **Passing** |
| **Directory traversal via filename** | `sanitizeFilename` strips path components, control characters, and parent directory traversal markers (`..`, `/`, `\`); disk storage uses random UUID filenames. | `tests/documents.test.js`: *"Upload rejects spoofed magic bytes, oversize files, and traversal filenames"* | **Passing** |
| **In-transit file modification / corruption** | Server computes SHA-256 and validates against browser-provided `clientSha256`, rejecting altered files with 400. | `tests/documents.test.js`: *"Upload rejects altered clientSha256 and duplicate upload by same owner returns 409"* | **Passing** |
| **Duplicate file upload spam** | Partial unique index on `documents(owner_id, sha256) WHERE deleted_at IS NULL` rejects duplicate active uploads by the same owner with 409. | `tests/documents.test.js`: *"Upload rejects altered clientSha256 and duplicate upload by same owner returns 409"*, `tests/schema.test.js` | **Passing** |
| **Tampered file delivery to users** | Server re-computes SHA-256 hash upon download from storage and compares against database record; on mismatch, it records an audit failure and returns generic 500 without sending data. | `tests/documents.test.js`: *"Tampered stored file fails download with generic 500 and audits integrity failure"* | **Passing** |
| **Document discovery via search** | Search endpoint enforces SQL-level filtering restricting returned results strictly to documents owned or granted to the requesting user. | `tests/documents.test.js`: *"Search never returns unreadable documents for ungranted users"* | **Passing** |
| **Undetected authorization denial attacks** | Every denied `authorize()` decision writes an audit record in a dedicated short transaction before throwing 404. | `tests/documents.test.js`: *"Denied attempts are audited in audit_log"* | **Passing** |
| **Administrative route enumeration** | Non-admin and anonymous callers requesting any `/api/admin/*` route receive a uniform 404 Not Found response. | `tests/admin.test.js`: *"Non-admin and anonymous callers receive 404 for all /api/admin routes"* | **Passing** |
| **Disabled user accessing resources via lingering session** | Disabling an account immediately deletes all associated session records in PostgreSQL within the same transaction; session middleware rejects disabled accounts. | `tests/admin.test.js`: *"PATCH /api/admin/users/:id/status disables user and ends their session immediately"* | **Passing** |
| **Inline browser script execution from uploaded documents** | Download responses set `Content-Disposition: attachment`, `X-Content-Type-Options: nosniff`, and `Cache-Control: no-store`. | `tests/documents.test.js`: *"Matrix: download authorization and headers"* | **Passing** |

## 2. Accepted Risks

| Threat | Mitigation Status | Technical Rationale & Context |
|---|---|---|
| **Process crash clearing in-memory rate limiters** | **Accepted** | Rate limits for registration and login attempts are maintained in process memory. A process restart resets active counters. Accepted for single-instance hackathon deployment. For multi-node high-availability clusters, Redis-backed rate limiting should be introduced. |
| **Database superuser modifying table records** | **Accepted** | Database triggers prevent regular application roles from executing `UPDATE`, `DELETE`, or `TRUNCATE` on `audit_log`. A PostgreSQL superuser or DBA with direct filesystem access could theoretically disable triggers. This is mitigated through database-level privilege separation and verifiable cryptographic hash chain auditing (`/api/admin/audit/verify`). |
| **Denial of Service via rapid repeated file uploads within 10 MB limit** | **Accepted** | File size is strictly capped at 10 MB per document and uploads require active session authentication. Rate limiting on document uploads is currently unenforced to avoid friction during high-frequency hackathon workflows. |
